# 二期候选：一次只推进一条使用流程

2026-10-16 用户补充。**状态：记录需求，尚未启动实现或确定架构。** 先按 [完整测试清单](FINAL_ACCEPTANCE_CHECKLIST.md) 完成一期逐项验收和反馈修复，再讨论下一条做什么。

## 已知意图

- 体验和 Control：减少第一次打开时的困惑，把必要配置放在合适时机；参考这轮实际测试反馈，不先塞一堆设置。
- 新卡片：仍复用真实 Assistant UI styled registry 和已批准组件，不手画卡片框架；先选一种有明确用途的卡片，完成数据/来源/动作/密度/布局/撤销/同步全链路再增加下一种。
- 账号：希望每个用户通过既有 Pi/OAuth 连接自己的账号，使用自己的能力与额度；不是共享站长的一个全局授权，也不是开发 coding agent/session/tools 或新 OAuth 协议。
- 内测：考虑内测码，以及输入邮箱等待邀请。现阶段只记录交互目标，不收集真实邮箱、不自动发邮件、不接入支付。
- 手机：研究手机浏览器作为 Control，用于语音输入、设置、拍照/选图；Display 依然保持简洁。可行性、跨设备同步与权限需要单独验证，不声称当前 BroadcastChannel 已支持手机跨设备配对。
- 服务器：研究合适的部署方式和多用户操作；先弄清个人设备与服务端分别承担什么，再选择方案，不直接把当前本机单用户服务暴露为多用户系统。

## 后续逐条梳理的顺序

1. 一期验收：按编号解决问题，汇总真正影响日常操作的摩擦。
2. 一条最小配置流程：从第一次打开到看到首张有用卡片；确认页面层级后才扩展 Control。
3. 一种新增卡片：查 Assistant UI 已有能力，给出真实复用和完整行为，再实现/验证。
4. 独立讨论部署边界：生产路由/认证代理、每人登录/凭据存储与刷新隔离、自己的额度、用户画布与请求隔离、跨设备状态传输、邀请/邮箱、退出/清除和运维成本。当前只验证本机开发代理，不把静态前端构建或本机全局 bearer 当成服务器多用户方案。若既有 OAuth 不支持拟定托管方式，应先实证再决定，不猜协议或承诺任意账号可用。
5. 用明确的一个账号/两个设备做手机 Control 原型，验证浏览器语音/相机或附件权限与同步；之后再扩大到邀请内测。

以上是候选拆解，不是一次性实施清单。具体先后可由一期结果调整；一次只推进一条经过说明的完整链路，验证后再做下一条。

## 仍然保留的约束

保持 Web、极简 Display、卡片/Action 白名单、真实数据与显式图片请求、既有 Pi/OAuth 能力边界；不因部署研究放宽私网抓取或把凭据写入浏览器/画布。当前音色复刻暂缓、全浏览器关闭提醒不需要，第三种远程 LLM/音乐/支付/桌面宿主不自动加入二期。
